# Supporter entitlements

`backend/app/core/entitlements.py` defines the Free and Supporter capabilities and free hosting limits. `users.plan` is `FREE` or `SUPPORTER`; `user_entitlements` holds optional per-user grants (for gifts or future providers). Roles remain separate from plans. Admins receive the Supporter capability set through server policy, preserving the existing super admin account without promoting every user.

The startup migration adds `users.plan` with a `FREE` default, the per-user grant table, room hosting mode and start time, and the private-room fields and access table. Existing rooms are classified as multiplayer so their links and guests keep working. Their hosting start time remains empty because historical solo launches cannot be identified reliably; they do not consume the new daily allowance. No payment provider is involved. The new tables are created by SQLAlchemy `create_all` on startup, matching this project's existing schema approach.

An admin can assign a plan with `PATCH /auth/admin/users/{id}/plan` and `{"plan":"SUPPORTER"}`. A grant can be added with `POST /auth/admin/users/{id}/entitlements` and `{"entitlement":"private_rooms"}`, or removed with `DELETE /auth/admin/users/{id}/entitlements/{entitlement}`. The signed-in account sees its effective plan and grants at `GET /auth/me`. Browser state is for display only; each premium API operation reads the database and applies the server policy.

Free players can browse, play, join public games and tournaments, host basic multiplayer rooms, and join private rooms by invitation or password. Free hosts may have up to three active multiplayer rooms and create up to twelve multiplayer rooms in 24 hours. Solo game rooms do not count toward either allowance. Their party rooms allow up to four players; a multiplayer arcade session allows eight connections. Supporters can create private rooms, host larger sessions, create tournaments, use built-in recording controls, and have no multiplayer hosting allowance. Tournament creators can manage their own tournaments; admins can manage all.

WebSocket signaling authenticates the bearer token sent as a WebSocket subprotocol, rejects guests from solo rooms, checks private-room admission, limits connections to the room's stored capacity, and rejects non-host room-control messages. Opening a solo arcade cabinet to multiplayer checks the same Free hosting allowance and records the conversion time. Switching it back to single-player does not refund the hosted room. This currently assumes the single Uvicorn worker used by `docker-compose.yml`; a multi-worker deployment needs shared connection state and capacity admission before scaling out.

Solo rooms have separate technical abuse protection for every account, including Supporters: at most 20 creations per minute, 240 per hour, and 12 rooms active in the last two minutes. HTTP creation and heartbeat checks return 429 with `Retry-After`, never an upgrade message. WebSocket admission also checks and records solo activity, closing an abusive connection with code 4429. A solo room with no host activity for 12 hours is marked expired when accessed or during its owner's next room creation. Its row and activity history remain for profile statistics. These thresholds protect the API and database; they are not a plan allowance.

**Deployment requirement: run exactly one backend worker and one backend replica.** The WebSocket connection list, per-room admission locks, connection count used for player capacity, and signaling broadcasts are process-local in `backend/app/websockets/signaling.py`. With multiple workers, each would admit players against only its own count, and messages would not reach players on other workers. Before scaling out, connection membership/capacity admission needs shared coordination and signaling events need pub/sub. The database already holds room configuration and entitlement state but does not solve live connection coordination.

Tournament creation alone requires `create_tournaments`. Existing creators and admins can reset or delete a tournament even after a creator's Supporter entitlement expires; the frontend uses the server's `can_delete` field for these controls.

Recording runs wholly in the user's browser via `MediaRecorder`; the Supporter UI lock does not make browser capture enforceable server-side. There is no recording API or server-stored recording to protect yet. `EARLY_ACCESS_SYSTEMS` and `EARLY_ACCESS_FEATURES` in the central policy are empty until a future release designates something for early access; existing tester and admin system rules remain separate. `AVATAR_ENTITLEMENTS` in the profile API is also empty: all eight current avatars remain Free. Future selected avatars can require `supporter_avatars`, checked by the server on avatar update and shown locked in the profile UI. No save-slot benefit is advertised.
