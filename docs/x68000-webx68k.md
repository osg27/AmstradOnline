# Sharp X68000 browser runtime

The X68000 room now uses the WebX68k PX68k core and browser host directly.
It previously used the shared PC Engine/EmulatorJS launcher. That runtime
reproducibly stopped responding after entering emulation with verified firmware
and a blank floppy. The direct WebX68k host completed frames and booted Human68k
in the same Chrome environment.

## Files and builds

- Room entry point: `frontend/public/x68000/launcher.html`.
- Room adapter source: `frontend/src/features/x68000/launcher.js`.
- Media preparation and joystick translation: `frontend/src/features/x68000/media.js`.
- Upstream host source: `frontend/src/features/x68000/vendor/webx68k/`.
- Unmodified core binaries and licence: `frontend/public/x68000/webx68k/`.
- Pinned revisions and corresponding source links: `frontend/public/x68000/webx68k/NOTICE.md`.

Run `npm run build:x68000` in `frontend` to rebuild the committed launcher bundle.
The normal production build also runs this step. No upstream BIOS or system disk
is included in the application; firmware comes from the existing browser storage
or room firmware picker. IPL and CG filenames are normalized independently of the
folder names in the supplied firmware archive.

Machines start with 12 MB of emulated RAM so larger games are not limited by
the original 2 MB configuration. This takes effect when the game is relaunched.
Single HDFs boot directly. Multiple floppy files are mounted using an M3U;
existing M3U/CMD files take precedence. ZIP contents retain relative paths so
playlists continue to reference their disks. Game URL sources use the existing
account-linked game-source scanner and download service.

The adapter handles the existing room joystick/keyboard/mouse, volume, pause,
reset and audio-unlock messages. Both `getX68000AudioStream` and the historical
`getPcEngineAudioStream` expose the captured audio stream for recording/WebRTC.
Audio uses the core's sample rate and a bounded playback queue. The browser
animation loop caps catch-up work; it does not run unbounded frame batches.

## Verification

Verified in local headless Chrome using existing local IPL/CG firmware:

- Human68k 3.02 floppy boot rendered the startup screen and completed 329 frames
  in the first six seconds without blocking browser evaluation.
- Pause stopped the frame counter; reset resumed execution in a fresh core.
- Synthetic HDF and two-floppy M3U launches remained responsive and completed
  more than 100 frames each. These checks validate media mounting and execution,
  not game compatibility or successful boot from the synthetic disks.
- The audio capture getter returned a live audio track. Audible game music and
  multiplayer input have not been manually verified.
- Media tests cover HDF selection, multi-floppy ZIP playlists, explicit playlist
  priority, unsafe paths and joystick translation.

The user's Chourensha HDF has not been tested locally. For diagnostics, inspect
`window.x68000Runtime` in the emulator frame; it reports engine, running/paused
state, completed frames and the most recent error. Startup stages are also sent
to the room as `x68000_trace` messages.
